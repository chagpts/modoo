06-01. 감사계획과 데이터 요청 범위 설계

CISA식 감사계획을 회계 데이터 요청목록으로 전환합니다. 이 과정은 실제 감사 현장에서 바로 설명할 수 있는 문제정의, 증거 수집, 예외 판단, 결론 작성까지 하나의 흐름으로 실습합니다.

실습 시나리오

감사팀은 신규 ERP 도입 후 첫 결산을 수행한 회사를 대상으로 감사 목적, 범위, 모집단, 데이터 소유자를 정의합니다. CISA 실무에서 강조하는 위험 기반 접근을 응용하여 어떤 데이터가 감사증거가 될 수 있는지 판단합니다.

핵심 감사위험: 범위가 넓어 필요한 로그와 거래 데이터가 누락되면 분석 결과가 편향될 수 있습니다. 반대로 불필요한 개인정보까지 수집하면 데이터 반출통제와 보안 문제가 발생합니다.

분석 설계 실습

CISA식 전산감사 관점에서 필요한 판단과 증거를 먼저 정의합니다. 단순 체크리스트가 아니라 왜 이 절차가 필요한지, 어떤 결론에 쓰이는지를 함께 작성합니다.

  • 감사목적별 데이터 요청목록 작성
  • 시스템·프로세스·계정별 데이터 소유자 식별
  • 읽기 전용 추출 권한과 반출 승인 절차 설계
  • 데이터 완전성 확인 항목 정의
  • 감사증거와 분석 결과의 연결 방식 설계

감사 활용 실습

회계 데이터 분석 적용으로 연결하여 수업 산출물이 실제 감사조서, 개선권고, 포트폴리오 설명 자료로 이어지도록 만듭니다.

  • 감사계획과 데이터 요청 범위 설계와 관련된 원천 데이터 또는 증거 위치를 식별합니다.
  • 정상 처리와 예외 처리를 구분하는 판단 기준을 작성합니다.
  • 검토 결과를 위험도, 영향도, 추가 확인 필요 항목으로 분류합니다.
  • 담당자 인터뷰 질문과 요청 증빙 목록을 만듭니다.
  • 최종 결론 문구와 개선 권고안을 작성합니다.

실습 데이터 예시

교육에서는 다음과 같은 필드를 가진 샘플 CSV 또는 엑셀 파일을 사용합니다. 데이터는 실무 자료와 유사한 구조로 만들되 개인정보와 회사 고유정보는 모두 제거한 가상 데이터로 구성합니다.

  • AUDIT_SCOPE: system_name, process, account, risk, data_owner
  • DATA_REQUEST: table_name, field_name, purpose, retention_period
  • EXTRACTION_LOG: request_id, extracted_by, extracted_at, row_count, checksum

교육 진행 흐름

  1. 1단계: 감사위험을 읽고 필요한 데이터 원천을 표시합니다.
  2. 2단계: 원천 데이터의 완전성과 정확성을 먼저 확인합니다.
  3. 3단계: SQL 또는 분석 규칙으로 전체 모집단 예외를 추출합니다.
  4. 4단계: 예외를 증빙 검토 결과와 연결해 실제 오류와 정상 예외를 구분합니다.
  5. 5단계: 분석 조건, 한계, 결론을 조서 형태로 정리합니다.

교육 산출물

  • 데이터 요청목록과 원천 검증표
  • 예외 추출 규칙과 분석 결과표
  • 감사조서용 결론 메모
  • 재수행 가능한 쿼리·코드 파일
