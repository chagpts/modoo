05-03. 프로그램 변경관리

ITAC 로직 변경이 승인·테스트·배포 절차를 거쳤는지 확인합니다.

실습 시나리오

매출 할인율 자동계산 로직이 분기 중 변경되었지만, 변경 요청서와 사용자 승인 증적이 일부 누락되어 있습니다. 학습자는 변경관리 증거와 ITAC 테스트 결과를 연결합니다.

핵심 감사위험: 자동통제 로직이 무단 변경되면 과거에는 정상 작동하던 ITAC도 감사대상 기간 중 특정 시점부터 오류를 발생시킬 수 있습니다.

과정 구분: ITGC 기반 ITAC

변경관리 설계 실습

프로그램 변경의 요청, 승인, 개발, 테스트, 배포 절차를 통제 관점으로 검토합니다.

  • ITAC에 영향을 주는 프로그램과 설정 테이블을 변경관리 모집단으로 정의합니다.
  • 변경 요청서의 업무 목적, 영향 범위, 승인권자를 검토합니다.
  • 개발자와 운영 배포자의 권한 분리 여부를 확인합니다.
  • 테스트 증적이 정상 케이스와 예외 케이스를 모두 포함하는지 평가합니다.
  • 긴급 변경이 사후승인 및 리뷰 절차를 거쳤는지 점검합니다.

변경 로그 분석 실습

변경 티켓, 소스 버전, 배포 로그를 비교하여 누락 또는 불일치 예외를 찾습니다.

  • 변경관리 시스템의 티켓 목록과 실제 배포 로그를 대사합니다.
  • ITAC 관련 프로그램의 변경일 전후로 재수행 테스트 기간을 나눕니다.
  • 소스 코드 또는 설정값 변경 내역에서 승인되지 않은 수정 이력을 추출합니다.
  • 테스트 실패 후 재배포된 건의 원인과 승인 증적을 검토합니다.
  • 변경관리 결함이 ITAC 운영평가 결론에 미치는 영향을 정리합니다.

감사 접근 비교 포인트

구분통제 설계 검토데이터 기반 운영평가
감사 초점변경관리 설계 실습에서 통제 설계와 책임 구조를 확인합니다.변경 로그 분석 실습에서 데이터와 시스템 결과로 운영 여부를 입증합니다.
증거 방식정책서, 승인 문서, 인터뷰, 화면 증거를 활용합니다.원천 테이블, 로그, 변경 이력, 재수행 결과를 활용합니다.
결론 연결통제 미비의 원인과 보완통제 필요성을 정리합니다.예외 건수, 금액 영향, 반복 가능 감사절차를 산출합니다.

실습 데이터 예시

교육에서는 다음과 같은 필드를 가진 샘플 CSV 또는 엑셀 파일을 사용합니다. 데이터는 실제 ERP와 감사조서 구조를 단순화하여 구성하고, 일부 오류를 의도적으로 반영합니다.

  • CHANGE_TICKET: ticket_id, application, control_id, request_date, approval_status
  • DEPLOY_LOG: ticket_id, program_id, deploy_date, deployed_by
  • CONFIG_HISTORY: control_id, parameter_name, old_value, new_value, changed_at

교육 진행 흐름

  1. 통제 이해: 업무 프로세스와 시스템 흐름을 읽고 통제 목적을 표시합니다.
  2. 위험 식별: 오류가 발생할 수 있는 입력, 처리, 출력, 변경 지점을 정리합니다.
  3. 증거 설계: 필요한 정책서, 화면, 로그, 테이블, 승인 증적을 정의합니다.
  4. 테스트 수행: 설계평가와 운영평가 절차를 수행하고 예외를 분류합니다.
  5. 결론 작성: 재무제표 영향, 통제 영향, 개선권고를 감사조서 문구로 작성합니다.
